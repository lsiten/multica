# Legacy runtime discovery / profile pin delta review

**Scoped verdict: FAIL — one correctness blocker.** This is a read-only source and focused-test review of the current dirty tree, not full product signoff. No source edits, real agent CLI execution, account/config reads, user repository mutations, commits, or deployment were performed.

## Blocker

**P2: A discovered legacy runtime is lost when the target or selected repository changes.** `packages/views/issues/components/local-review-dialog.tsx:23-26` includes repository path and target in the snapshot query key and retrieves discovered `runtime_id` only from that exact key. The original request remains without a runtime for legacy inventory entries. Applying another target therefore passes `runtime_id: undefined`, even after the previous target successfully discovered the runtime and an approval persisted `.review-runtime.json`. `apps/desktop/src/main/local-review-request.ts:21-24` consequently calls remote discovery again. When the server becomes unreachable this throws before the daemon health/direct request; the already verified local owner can no longer review another target in the same dialog. The same identity loss occurs on selecting another repository. Returning to a previously cached target happens to work.

Reproduction contract: open a legacy task lacking request.runtime_id; receive runtime_id R for main; approve to persist provenance; make discovery unavailable; apply release. The new query has no R and rejects during discovery instead of accessing the owner daemon. Current dialog tests cover target application but provide no runtime metadata and assert no cross-target identity retention. The main helper's “discovers ... once” test manually supplies the first result's runtime on its second invocation; it does not exercise this dialog behavior.

Required correction: retain verified task runtime independently of target/path (scoped to task/workspace and suitable account/profile identity), or consult local persisted inventory before repeating discovery. Add a regression that changes targets/repositories after discovery and proves further local requests retain R without a second cloud lookup. Do not widen the snapshot cache itself across targets.

## Contracts that passed inspection

- **Profile pin:** `requestLocalReview` resolves a profile once and supplies the selected object to discovery, health, and review. `daemon-manager.ts:209-241,1412-1427` passes that profile into `fetchWorktreeManager`, which does not re-resolve it. Health validates profile plus workspace/runtime membership. A different selected profile's port cannot replace the already selected port between awaits. Credentials are re-read by profile name, rather than pinned; a token change can fail authentication. This is an availability/failure boundary, not evidence of cross-account authorization bypass.
- **Discovery identity and authorization:** `local_review_binding.go:12-57` loads stored task/runtime metadata, requires the runtime's owner user or matching daemon through `localReviewRuntimeForID`, checks task workspace, and sends `Cache-Control: no-store`. Desktop parses nonempty IDs and compares discovered workspace/task with the requested ones before health access. The daemon compares runtime/task/workspace again. No MR state is written by these binding endpoints.
- **Legacy provenance:** `worktree_review.go:165-182` falls back to metadata verification only on a missing provenance file; malformed or mismatched existing data fails closed. The request carries the verified binding into the later locked phase. `local_review_legacy.go:31-46` preserves existing matching provenance, rejects a changed identity, and writes only when missing. The normal decision path persists under task reservation and cross-process environment lock (`worktree_review.go:223-251`). Subsequent decisions use local provenance without re-verifying remotely.
- **Recovery integration:** `local_review_recovery.go:23-53` reserves/locks the environment and persists verified legacy identity before source/repository claims and recovery receipt work. Failure returns a conflict and avoids proceeding to merge recovery. The local preflight precedes the recovery call. The reviewed delta does not introduce cloud MR persistence or change remote relay transport.
- **Failure handling:** unavailable discovery throws visibly; non-owner health returns null for relay routing; absent/mismatched legacy binding rejects decisions; persistence errors abort. An account/profile change does not erase server and daemon authorization checks. Live switching while requests are in flight has not been exercised.
