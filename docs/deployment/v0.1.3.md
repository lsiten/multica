# v0.1.3：已有 Docker Compose 部署升级

适用仓库：`lsiten/multica`，公开访问地址：`https://multica.lene.fun/`。
本次发布 backend/web 镜像（amd64、arm64），不发布桌面安装包。

## 版本与升级顺序

等待 GitHub Actions 的 **Fork Images** 工作流中 **publish** 成功后再升级：

- `ghcr.io/lsiten/multica-backend:v0.1.3`
- `ghcr.io/lsiten/multica-web:v0.1.3`

两个服务必须使用同一版本。服务器只拉镜像，不需要本机 build。
若拉取提示 `unauthorized`，先检查 GHCR 包的可见性；公开仓库不等于镜像包公开。私有包需先用具有 `read:packages` 权限的凭据登录 GHCR，并通过 `docker login --password-stdin` 输入令牌，不要写入仓库或命令参数。
升级顺序为：备份并升级服务端 → 更新每台任务机器的守护进程 → 刷新网页/重启开发版桌面端 → 验证 MR。

本地 MR 数据保存在运行时机器，服务端仅鉴权、查询既有任务身份和临时转发。
本次 MR 功能不新增数据库表。后端启动仍自动执行既有迁移，失败时不会启动 API；不要手动执行 migration down。
若曾自行部署中间开发版本的 MR 表，此版不会自动删除那些表，请保留并备份，不要手动清表。

## 1. 确认现有配置

以下命令都在当前部署目录运行，并在同一个 shell 中完成。

```bash
docker compose -f docker-compose.selfhost.yml ps
docker compose -f docker-compose.selfhost.yml config --images
```

镜像应来自上述两个 `ghcr.io/lsiten` 仓库。若旧 Compose 仍含本地 `build:` 或使用其他仓库，先备份文件，再参考本 tag 的 `docker-compose.selfhost.yml` 合并镜像配置。
保留现有自定义端口、反向代理和卷名。若现有部署使用 `-p`、`--env-file` 或额外 `-f`，下面每条 Compose 命令都应保留相同参数。

**不要**用 `.env.example` 覆盖现有 `.env`。必须保留原来的 `JWT_SECRET`、数据库密码、通知机器人和各集成的加密密钥，否则可能导致会话失效或已有配置无法解密。
公网地址仍应使用 HTTPS；容器间 `REMOTE_API_URL=http://backend:8080` 不需要改成公网域名。

## 2. 先拉取，备份后再替换容器

让运行中的任务结束，并选择维护窗口。备份目录包含敏感配置，不要提交到 Git。

```bash
set -e
backup_dir="../multica-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup_dir"
cp .env "$backup_dir/.env"
cp docker-compose.selfhost.yml "$backup_dir/docker-compose.selfhost.yml"

backend_container=$(docker compose -f docker-compose.selfhost.yml ps --all --quiet backend)
frontend_container=$(docker compose -f docker-compose.selfhost.yml ps --all --quiet frontend)
test -n "$backend_container"
test -n "$frontend_container"
backend_image_id=$(docker inspect --format '{{.Image}}' "$backend_container")
frontend_image_id=$(docker inspect --format '{{.Image}}' "$frontend_container")
rollback_tag="before-v0.1.3-$(date +%Y%m%d%H%M%S)"
docker tag "$backend_image_id" "multica-backend-rollback:$rollback_tag"
docker tag "$frontend_image_id" "multica-web-rollback:$rollback_tag"
printf '%s\n' "$rollback_tag" > "$backup_dir/rollback-tag.txt"

MULTICA_IMAGE_TAG=v0.1.3 docker compose -f docker-compose.selfhost.yml pull backend frontend

docker compose -f docker-compose.selfhost.yml stop frontend backend
docker compose -f docker-compose.selfhost.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_dir/database.dump"
test -s "$backup_dir/database.dump"
docker run --rm --volumes-from "$backend_container" --entrypoint tar \
  "$backend_image_id" -C /app/data -czf - uploads > "$backup_dir/uploads.tar.gz"
test -s "$backup_dir/uploads.tar.gz"
```

这会短暂停止 API/网页，PostgreSQL 和持久卷继续保留。若备份失败，不要继续升级；可以用 `docker start "$backend_container" "$frontend_container"` 启动原容器。
另行备份各运行时机器的工作区目录，尤其是 `.local-mr-archive` 和未推送的 Git 改动；它们不在服务端数据库或上传卷中。

## 3. 固定版本并启动

编辑现有 `.env`，只把 `MULTICA_IMAGE_TAG` 改为下值（不存在则新增，避免重复定义）：

```dotenv
MULTICA_IMAGE_TAG=v0.1.3
```

```bash
MULTICA_IMAGE_TAG=v0.1.3 docker compose -f docker-compose.selfhost.yml \
  up -d --no-build --no-deps backend frontend
docker compose -f docker-compose.selfhost.yml ps
docker compose -f docker-compose.selfhost.yml logs --tail=100 backend
curl -fsS https://multica.lene.fun/api/config
```

等待后端日志依次出现迁移完成和 API 启动，再打开网页。`/api/config` 应包含 `server_version: "v0.1.3"` 与 `local_review_supported: true`。
看到旧版本先检查实际容器镜像、反向代理目标和是否有旧容器仍接收流量，不要反复 build。
日志可能包含业务信息，公开反馈前请脱敏。

**禁止使用 `docker compose down -v`、删除 `pgdata` 或清空上传卷来升级。**

## 4. 运行时机器也要更新

仅更新 backend/web 镜像，不会更新另一台电脑上的守护进程。旧守护进程不能处理新的 MR 转发请求。
保留原 profile、服务端地址、工作区目录及登录配置，不要创建一个空 profile 来替代原运行时。

### 桌面端托管 / 本地 dev

等待运行结束，退出原开发版桌面端。在源码目录更新到本版本（有未提交改动先备份，不要强制 reset），安装锁定依赖后运行：

```bash
git fetch origin --tags
git switch --detach v0.1.3
pnpm install --frozen-lockfile
pnpm dev:desktop
```

该 dev 命令会先构建 CLI，再启动桌面端。旧安装版 App 不会因服务端升级自动获得新 IPC 功能；本次没有发布安装包。
桌面端托管的守护进程不要同时另起一个独立实例或单独覆盖 PATH 中的 CLI，以免桌面端再次拉起旧二进制。

### Linux 独立运行时：从已构建镜像提取 CLI

在该运行时机器上执行，Docker 会选择对应 Linux 架构；提取出的文件不能在 macOS 上运行。

```bash
test ! -e ./multica-v0.1.3
runtime_extract="multica-cli-v013-$(date +%s)"
docker create --name "$runtime_extract" ghcr.io/lsiten/multica-backend:v0.1.3
docker cp "$runtime_extract:/app/multica" ./multica-v0.1.3
docker rm "$runtime_extract"
chmod +x ./multica-v0.1.3
./multica-v0.1.3 --version
```

确认没有运行中的任务后，用原来的 profile（以下是占位值，必须替换）停止并启动：

```bash
runtime_profile="你的原profile名称"
./multica-v0.1.3 --profile "$runtime_profile" daemon stop
./multica-v0.1.3 --profile "$runtime_profile" daemon start --no-auto-update
./multica-v0.1.3 --profile "$runtime_profile" daemon status
```

`--no-auto-update` 防止 fork 的运行时被默认上游更新源替换。原来使用默认 profile 的，省略 `--profile` 参数；systemd 等托管方式应更新原服务的二进制路径与参数，不要重复启动。
macOS 独立 CLI 可在对应机器用 Go 1.26 从本 tag 构建 `server/cmd/multica`；不能复制容器里的 Linux 二进制。

## 5. 功能验收与限制

- 运行时页面确认机器在线、CLI 为新版本。
- 从任务关联 worktree、智能体的工作页、工作区管理分别打开 MR，确认分支、路径和 diff 对应正确的运行。
- 先用可丢弃的测试分支验证提交、批准、请求修改和二次确认合并，不要直接用业务主分支试验。
- 桌面端连接对应本机运行时时直连守护进程；其他机器及普通网页版通过服务端代理。旧目录首次识别可能需要一次服务端身份核对。
- 运行时离线时无法读取最新 Git 数据；不会回退到云端 MR 快照。
- 此 Compose 为单 backend 实例；本版临时转发队列不支持无路由协调的多 backend 副本。
- Git clean/process 等命令过滤器在检查时被禁用，展示原始工作文件；LFS 等转换语义不做等价保证。

## 6. 回滚

不要删除备份、旧镜像标签和数据卷。若需要先回退应用镜像，使用步骤 2 保存的本机标签：

```bash
# 换终端后，先从备份中的 rollback-tag.txt 取回 rollback_tag。
MULTICA_BACKEND_IMAGE=multica-backend-rollback \
MULTICA_WEB_IMAGE=multica-web-rollback MULTICA_IMAGE_TAG="$rollback_tag" \
docker compose -f docker-compose.selfhost.yml \
  up -d --no-build --no-deps --pull never backend frontend
```

同时把 `.env` 的镜像变量恢复为所选旧版本配置。上面的环境覆盖用于立即回滚，不能代替持久配置。
镜像回退不撤销迁移。若从很老的版本升级导致数据库不兼容，应在维护窗口用备份恢复到独立数据库验证后再切换；不要对业务库盲目执行 `pg_restore --clean` 或迁移降级。

企业微信通知会在 GitHub 确认两个多架构镜像发布成功后发送；通知不代表已替你操作生产服务器。Webhook 属于凭据，不应放进仓库、Compose 文件或日志。
