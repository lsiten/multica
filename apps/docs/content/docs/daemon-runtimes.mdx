Multica records and coordinates the work; connected computers execute it. The **daemon** on a computer claims runs and invokes the AI coding tools installed on that machine.

## Daemon vs runtime

- The **daemon** is the Multica background process running on one computer. It connects to the server, discovers local tools, claims runs, and reports results back.
- A **runtime** represents one concrete execution environment available to a workspace. It corresponds to one computer plus one AI coding tool — or one custom runtime profile — on that computer.

For example, a computer has both Claude Code and Codex installed and is connected to two workspaces. The daemon registers Claude Code and Codex runtimes for each workspace. Restarting the daemon updates the existing records; it does not keep creating new runtimes for the same combination.

## Execution location and data boundaries

The AI coding tools a local runtime invokes, those tools' own login credentials, and your local code directories all stay on the connected computer. The Multica server does not execute commands on behalf of local tools, and it does not automatically upload your entire working directory.

So the team can collaborate, the server stores issues, comments, agent configuration, run context, run records, and the results agents write back. That content can include code snippets or other project context an agent chose to read and include in its replies.

<Callout type="warning">
An agent's custom environment variables are stored server-side and sent to the runtime at execution time. Do not read "local execution" as "every secret exists only on this machine": custom environment variables and MCP configuration live on the server, and their display is limited by the sensitive-value rules.
</Callout>

## Starting the daemon

With Multica Desktop, the app starts the daemon automatically — no extra command needed.

On the web, a remote computer, or a headless environment, [install the Multica CLI](/cli) first, then run:

```bash
multica daemon start
```

The daemon runs in the background by default. Common commands:

| Command | Purpose |
| --- | --- |
| `multica daemon status` | Show daemon and connection status |
| `multica daemon logs -f` | Follow the logs |
| `multica daemon restart` | Restart the daemon and re-detect local tools |
| `multica daemon stop` | Stop the daemon |
| `multica daemon start --foreground` | Run in the current terminal, for debugging |

To place run workspaces on another disk, persist a root for the current profile with `multica config set workspaces_root <path>`, or pass `--workspaces-root <path>` to `daemon start` or `daemon restart`. The flag overrides `MULTICA_WORKSPACES_ROOT`, which overrides the profile config. Existing run directories are not moved when the root changes.

On startup, the daemon detects supported AI coding tools on `PATH` and registers runtimes for the workspaces you are allowed to connect. If a tool was just installed or signed in, restart the daemon to detect it again.

The daemon needs at least one built-in supported AI coding tool detected before it will start. Install methods and executable names are in [Install AI coding tools](/install-agent-runtime).

## Dispatch and online status

Once registered, a runtime keeps a persistent connection. When a new run enters the queue, the server notifies the matching daemon; the daemon also polls periodically as a backstop after connection interruptions. So when a runtime is online with spare capacity, runs usually start immediately.

The daemon sends a heartbeat every 15 seconds. The server combines heartbeats and connection state to decide whether a runtime is online; after a daemon exits unexpectedly, the runtime usually shows as offline within about 3 minutes at the latest.

![Runtime details for one online computer: the same daemon registered 7 runtimes, one row per detected AI coding tool, each showing online status and CLI version](/images/docs/runtime-machine-detail.webp)

When a runtime is offline:

- Runs already queued wait for the runtime to recover. They fail only once it has stopped heartbeating for longer than the reconnect grace **and** the run has itself been queued that long, so a runtime that is merely busy keeps its backlog, and work assigned to an already-offline runtime still gets a full grace to wait.
- Runs that were in progress fail; eligible issue or chat runs can retry automatically.
- When the daemon starts again, it re-registers its runtimes and reclaims runs that did not end cleanly last time.
- A runtime offline for more than 7 days with no agents bound to it (including archived ones) is cleaned up automatically.

Detailed states and retry rules are in [Runs](/tasks).

## Concurrency limits

One daemon executes at most 20 runs at a time by default; each agent at most 6. Effective concurrency is the smaller of the two.

Once a limit is reached, new runs keep queueing. You can adjust a single agent's concurrency in the agent settings, and the machine-wide cap through `MULTICA_DAEMON_MAX_CONCURRENT_TASKS`. Parallel runs compete for machine capacity, tool account quota, and the same working directory all at once.

## Private and public runtimes

A local runtime is **private** by default: only the runtime owner can create agents on it. Workspace owners and admins are no exception — the runtime is someone else's computer, and running an agent there spends their machine and their tool credentials.

Only the runtime owner can make it **public** — workspace admins can rename or delete a runtime, but sharing one is the owner's decision. Other workspace members can then select this runtime as well; that does not share the underlying AI coding tool's login credentials — it only lets members route their agents' runs to this computer.

## Runtime virtual screen

On a supported Mac, a runtime can own one managed virtual screen. Enable or disable it in that runtime's screen controls. The display belongs to the runtime, not an individual run or viewer; closing a mirror window leaves it enabled in the background. Runs on that runtime queue for exclusive GUI control while ordinary coding work can continue independently.

The mirror is view-only. Switching between the runtime's virtual screen and a physical display changes what you watch; it does not give an agent control of the physical display. Viewing another computer also does not grant local takeover rights.

### Permissions and supported apps

The native host is part of the bundled Multica executable on macOS arm64 and Intel. It requires available macOS virtual-display APIs, Screen Recording for capture, and Accessibility for app control. Creating a display alone does not establish capture or app-control permission. There is no separate driver or helper app to install. Linux, Windows, a build without native support, or a Mac missing the required APIs cannot provide this virtual-screen capability. Upgrading only the client does not add capabilities to an old daemon.

Grant permissions yourself in macOS **System Settings → Privacy & Security** for the installed Multica identity shown by the system. A permission shown for a development terminal or a different build is not proof that the installed Desktop has access. Diagnostics never request or reset permissions. An unknown permission, denied permission, unavailable source, or disconnected runtime is not ready for GUI work.

Managed tools can discover installed apps and list windows already managed by the runtime. A later run can reuse a managed window, including one returned after human intervention, but must obtain a fresh observation before acting. Discovery alone does not launch, move or take control of a window.

Managed tools use Accessibility actions supported by the target app. Production PID-targeted input requires reviewed evidence for the app, OS and action variant (including the input source for keyboard actions), plus a code-owned verifier of target processing and the resulting effect. The current production policy has no enabled PID variants; dispatch returning successfully is not a completion acknowledgement. An app that cannot stay within the managed screen or safely accept background input requires human intervention. These guarantees cover managed tools, not every command or external MCP an agent could invoke. This is not an OS sandbox.

The view-only mirror and agent observations have different data paths. An agent's observation can include a screenshot and Accessibility content supplied to its AI provider. Do not place sensitive content in a managed app unless that use is intended.

### Human handoff and cleanup

When a run needs help, its GUI actions are frozen and the original run is stopped. The owner on the same computer can explicitly take over, complete the required step, and return control. Continue creates a linked follow-up run after the return is verified; it does not resume the original run in place. The follow-up must observe the current window before taking another action. If continuation is unavailable, starting a fresh run requires an explicit choice.

If launch failed before a window was managed, the local owner can list safely selectable windows and explicitly confirm adoption. Adoption registers the selected window without automatically moving or activating it; candidate titles stay on the local Desktop. Returning it to the virtual screen requires a fresh observation and verified return receipt before Continue. Missing report acknowledgements keep the handoff waiting. A remote viewer can request help but cannot select local candidates or perform the local handoff.

Disable the virtual screen when you no longer need it. Disabling waits for input and capture to stop before disposing of the display. Closing the viewer only ends viewing. If cleanup, return, or display identity cannot be confirmed, keep the state blocked and inspect the reported failure; do not treat a timeout as successful cleanup or replay an uncertain action. After a restart or permission change, check the current runtime state again.

### Inspecting a packaged build

From a source checkout, inspect the exact app you intend to use:

```bash
pnpm --filter @multica/desktop exec node scripts/vscreen-native-smoke.mjs \
  --app /absolute/path/Multica.app --scenario package \
  --evidence /absolute/path/new-evidence-directory
```

The `package` report records bundle identity, helper path and SHA-256, architecture, linked frameworks, version/commit and signature verification. An ad-hoc signature is labelled as such; it is not evidence of notarization. `diagnostics` performs a nonprompting native/permission preflight. Its default direct-helper launch records that invocation's permissions, not Desktop's TCC attribution. Missing permissions or an older helper without diagnostics returns a nonzero result.

Add `--launcher desktop` to run diagnostics or a supported GUI scenario through the selected App's isolated main process and its verified bundled helper. This starts an actual App instance without loading the normal account/session startup. `desktop_launch_verified` confirms the process chain; it does not establish `tcc_attribution_verified`. Neither launcher requests, grants or resets permissions.

GUI scenarios require explicit `--allow-gui` or `MULTICA_RUN_VSCREEN_GUI_SMOKE=1`. They use disposable test resources and do not record the main physical screen by default. Each report retains its own scope and cleanup results:

| Scenario | What it exercises | What a pass does not establish |
| --- | --- | --- |
| `lifecycle`, `sources` | Create a test-owned display, match display/source identities and verify disposal. | App input or renderer playback. |
| `video` | Capture three H264 samples from the virtual display, with parameter sets, timestamps and hashes. | Renderer playback or end-to-end latency. |
| `background-input` | AX press/value changes in a copied-helper fixture, fresh readback and refusal of uncertified PID input. | Installed-app compatibility, positive PID actions, IME or continuous foreground typing. |
| `takeover` | Stop/revoke, local-owner transfer, virtual return, fresh observation, receipt and follow-up observation through an owned provider and loopback fixture backend. | Real database or Desktop UI acceptance, a real model, or manual human handoff; the fixture's human stage is scripted. |
| `input-qualification` | Experimental PID click, Unicode, key, scroll and drag effects in a same-bundle disposable fixture, with target completion ACKs and fresh observations. Requires `--launcher desktop`. | Production app certification. Foreground typing stays unverified unless `--interactive` is explicitly selected and the user completes the separate scratch-window challenge. |
| `performance` | Dynamic virtual content, two Chromium viewers, rendering/latency observations, resource samples and cleanup cycles. | Physical scanout latency, benchmark-specific GPU attribution or LAN acceptance from a local loopback run. |

`sources` and `background-input` are the canonical names; `source` and `input` remain aliases. The interactive qualification stage never writes the challenge text for the user or automatically activates the scratch window. Its manual-fixture result does not certify arbitrary installed apps or replace production evidence.

Formal performance acceptance requires at least 30 minutes and 30 lifecycle cycles. Short/debug runs are not acceptance. The default session uses same-host loopback: `localMeasurement` may pass while the overall assessment remains blocked for missing LAN evidence.

`all` runs the six required scenarios from `lifecycle` through `performance` (excluding experimental `input-qualification`). Its `missingCoverage` gate is independent of individual fixture results: positive production PID actions, installed-app compatibility, continuous foreground typing, Desktop UI/database/manual handoff and LAN coverage remain separately required. Unconfirmed cleanup prevents further GUI launches. Passing packaging, diagnostics or a fixture scenario does not satisfy these remaining gates.


#### Controlled remote performance viewer

Remote viewing is available to `performance` and `all` only, with both `--remote-viewer-config` and `--allow-remote-viewer`, in addition to the host GUI opt-in. In `all`, only the performance child reads this configuration or starts a remote process; other coverage gates remain independent. Authorize the second machine and host native GUI work separately before running it.

The configuration must be an absolute path to an owned, single-link, non-symlink regular JSON file, mode `0600`, at most 64 KiB. It accepts exactly these required fields:

| Field | Requirement |
| --- | --- |
| `schema_version` | `1`. |
| `host` | Explicit DNS name or IPv4 address, not an SSH alias, wildcard or IPv6 address. |
| `port` | Integer from 1 to 65535. |
| `user` | Explicit SSH account; ASCII letters/digits/underscore initially, then letters/digits/underscore/dot/hyphen, at most 64 characters. |
| `known_hosts_file` | Absolute path to a separate file containing exactly one three-field public host-key entry, without comments, aliases or hashed host names. Use the exact `host` for port 22, otherwise `[host]:port`. Supported key types are `ssh-ed25519`, `ecdsa-sha2-nistp256` and `ssh-rsa`. |
| `host_key_sha256` | Matching host-key fingerprint in `SHA256:` form, without base64 padding. |
| `identity_file` | Absolute path to the existing private key used for noninteractive authentication. |
| `remote_node` | Absolute Unix path to the existing remote Node executable. |
| `remote_repo` | Absolute Unix path to the matching remote repository checkout. |
| `worker_hash` | Matching 64-character lowercase SHA-256 from the worker command below. |

Both referenced local files must also be owned, single-link, non-symlink regular files, mode `0600`, at most 64 KiB. Remote Node/repository paths allow only ASCII letters, digits, `_`, `.`, `/` and `-`; `..` components, spaces, `~` and shell syntax are rejected. SSH uses only the declared key and a private snapshot of the pinned host-key entry: no agent, password prompt, ambient SSH configuration, global known-host fallback or forwarding is used.

The remote Mac or Linux machine must already have the matching worker sources, the repository-root `@playwright/test` installation and Chromium. Nothing discovers or installs these prerequisites. From the repository root on each machine, obtain and compare the worker hash without starting SSH or a browser:

```bash
node apps/desktop/scripts/vscreen-remote-worker.mjs --hash
```

After preparing the private configuration and a freshly packaged App with the matching producer/viewer implementation:

```bash
pnpm --filter @multica/desktop exec node scripts/vscreen-native-smoke.mjs \
  --app /absolute/path/Multica.app --scenario performance --launcher desktop \
  --allow-gui --remote-viewer-config /absolute/path/private-remote-viewer.json \
  --allow-remote-viewer --evidence /absolute/path/new-remote-evidence
```

The producer authorization nonce stays on the host; do not add it to the configuration or command line. Host-side signaling relays requests to the producer. The worker starts fresh headless Chromium contexts, not a user browser profile.

Remote source support is not a LAN acceptance result. A pass requires observed distinct machine identities, matching source/certificate/session evidence, selected direct UDP pairs and confirmed physical on-link routes on both ends, plus all existing duration, resource and cleanup gates. Missing OS tools, unknown routes, loopback, tunnels or relays block the result. Machine identity is trusted-OS evidence, not hardware attestation. Local headless tests cannot establish LAN coverage; real two-machine/native authorization and successful observations are still required.

## Custom runtime profiles

If your team uses an internal wrapper, a version-pinned executable, or needs fixed extra arguments for a compatible tool, create a **custom runtime profile**.

A custom profile does not add a new communication protocol. You still pick one of the protocol families Multica already supports (the tool's integration protocol type; see [AI coding tools comparison](/providers)), and the command itself must be compatible with that family.

### Task runtime environment

When the daemon starts an agent task, it injects task context into the runtime process. These values are owned by the daemon: an agent's custom environment cannot override any `MULTICA_` variable or the task temporary-directory variables.

The table lists the variables that custom runtimes can use today. It is intentionally not exhaustive and is not a versioned API surface. Build integrations only on the five variables marked **integration contract**; treat the rest as informational details that may change.

| Variable | Value in a task | Stability |
| --- | --- | --- |
| `MULTICA_TOKEN` | Task-scoped `mat_` API credential | **Integration contract** |
| `MULTICA_TASK_ID` | ID of the active task | **Integration contract** |
| `MULTICA_AGENT_ID` | ID of the assigned agent | **Integration contract** |
| `MULTICA_WORKSPACE_ID` | ID of the task's workspace | **Integration contract** |
| `MULTICA_SERVER_URL` | Multica server URL selected by the daemon | **Integration contract** |
| `MULTICA_TASK_CONFIG_ROOT` | Private task-local Multica CLI configuration root | Informational |
| `MULTICA_TASK_WORKSPACES_ROOT` | Root of the daemon-managed task workspaces | Informational |
| `MULTICA_AGENT_NAME` | Display name of the assigned agent | Informational |
| `MULTICA_DAEMON_PORT` | Local daemon health/API port used by task-only commands such as `multica repo checkout` | Informational |
| `MULTICA_TASK_SLOT` | Slot in the daemon-wide concurrency pool; useful for slot-indexed resources such as GPUs | Informational |
| `TMPDIR` | Private temporary directory for the active task; also supplied as `TMP` and `TEMP` for cross-platform tools | Informational |

The server determines authorship for requests made with `MULTICA_TOKEN`; writes such as issue comments are attributed to the assigned agent and active task. For the token's complete binding, permissions, attribution, 24-hour maximum lifetime, and cleanup behavior, see [Temporary tokens for agent runs](/auth-tokens#temporary-tokens-for-agent-runs).

<Callout type="warning">
These values live in the runtime process's real environment. Any child process the runtime starts inherits all of them by default, including `MULTICA_TOKEN`. If a child should not hold the credential, strip it explicitly; do not rely on process isolation that is not there. The exception runs the other way: tools that filter their own subprocess environment may require an explicit allow rule. For example, Codex's shell tool drops names containing `TOKEN`, `KEY`, or `SECRET`, so the daemon installs a managed shell policy that allows the required task variables. Keep the token in process environments only—never in a prompt, log, repository file, or persistent configuration. A child shares the parent task's identity and permissions; it does not receive a new, independently scoped identity.
</Callout>

### Creating a profile

Only workspace owners and admins can create, edit, or delete custom runtime profiles:

1. Open **Runtimes** and go to a computer where the command is installed.
2. Click **Add custom runtime**.
3. Choose the protocol family the command is actually compatible with.
4. Fill in the name, command, and fixed arguments, then save.

The profile is shared across the workspace. Each connected computer looks up the command on its own; only computers that can resolve it on `PATH` register the corresponding runtime. Creating a profile does not install the command, and it does not sign other members in to the tool.

The command field takes an executable and arguments, not a shell script. Plain arguments, quotes, and backslash escapes work; pipes, redirects, `&&`, `;`, backticks, and environment variable expansion do not. When you need those behaviors, put them in a wrapper script and use that script as the command.

### How your arguments are ordered

Everything you type in the command field stays directly after the executable, ahead of the arguments Multica adds:

```text
<your command> <your fixed arguments> <Multica's protocol arguments> <the agent's custom arguments>
```

This is what makes a subcommand-style wrapper work. If your command is `ccms start q36`, the tool sees `start q36` first and can select its subcommand before Multica's `-p` and the rest arrive — which is the only order such a wrapper accepts.

Your arguments used to be appended last instead. Most flag-style commands parse the same either way, but not all of them do — a command that distinguishes global flags from subcommand flags can care where a flag sits. If you already have a profile with fixed arguments, start one run on it after upgrading to confirm it still works.

Two more consequences worth knowing:

- **Multica's own values win a conflict.** If your fixed arguments set a flag Multica also sets, Multica's value comes later and takes effect. Most importantly, a model chosen on the agent overrides a `--model` pinned in the profile. To pin a model for everyone, leave the agents' model field empty.
- **Protocol-critical flags are ignored.** `-p`, `--output-format`, `--input-format`, `--permission-mode`, and the equivalents for other families are dropped from your fixed arguments, because overriding them would break the daemon's connection to the tool. Subcommands and other positional arguments always pass through.

If a Desktop-launched daemon cannot find a command your terminal can run, set an absolute path for the current computer:

```bash
multica runtime profile set-path <profile-id> --path /absolute/path/to/command
```

Remove the path override:

```bash
multica runtime profile unset-path <profile-id>
```

Editing a profile only affects runs claimed afterwards. Before deleting a profile, deal with the active agents still bound to its runtimes. Deleting only the runtime instance on one computer does not delete the profile — a running daemon will re-register it.

## Troubleshooting an offline runtime

Check in this order:

1. Run `multica daemon status` to confirm the daemon is running.
2. Run `multica daemon logs -f` to look for login, network, or tool-detection errors.
3. Run `command -v <tool-command>` in the same environment to confirm the daemon can find it.
4. Open Multica's **Runtimes** page and check whether the target computer and the matching AI coding tool show as online.
5. After a tool install, a path change, or a profile update, run `multica daemon restart`.

If the problem persists, see [Troubleshooting](/troubleshooting).
