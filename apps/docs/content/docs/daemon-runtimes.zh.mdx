Multica 负责记录和协调工作，连接的电脑负责执行。电脑上的**守护进程**（daemon）领取运行，再调用本机安装的 AI 编程工具。

## 概念区分

- **守护进程**是运行在一台电脑上的 Multica 后台程序。它负责连接服务器、发现本机工具、领取运行和回传结果。
- **运行时**代表一个工作区可以使用的具体执行环境。它对应一台电脑，以及这台电脑上的一款 AI 编程工具或自定义运行时配置。

例如，一台电脑同时安装了 Claude Code 和 Codex，并连接两个工作区。守护进程会分别为两个工作区注册 Claude Code 和 Codex 运行时。重启守护进程会更新原有记录，不会为同一个组合不断创建新运行时。

## 执行位置与数据边界

本地运行时调用的 AI 编程工具、这些工具自己的登录凭据，以及本地代码目录都留在连接的电脑上。Multica 服务器不会代替本地工具执行命令，也不会自动上传整个工作目录。

为了让团队能够协作，服务器会保存任务、评论、智能体配置、运行上下文、执行记录和智能体写回的结果。这些内容可能包含智能体主动读取并写入回复的代码片段或其他项目上下文。

<Callout type="warning">
智能体的自定义环境变量保存在服务器侧，并在执行时发送给运行时。不要把"本地执行"理解为所有 secret 都只存在本机；自定义环境变量和 MCP 配置保存在服务器侧，展示受敏感信息规则限制。
</Callout>

## 启动守护进程

使用 Multica Desktop 时，应用会自动启动守护进程，不需要额外运行命令。

使用 Web、远程电脑或无界面环境时，先[安装 Multica CLI](/cli)，再运行：

```bash
multica daemon start
```

守护进程默认在后台运行。常用命令如下：

| 命令 | 作用 |
| --- | --- |
| `multica daemon status` | 查看守护进程和连接状态 |
| `multica daemon logs -f` | 持续查看日志 |
| `multica daemon restart` | 重启守护进程并重新检测本机工具 |
| `multica daemon stop` | 停止守护进程 |
| `multica daemon start --foreground` | 在当前终端中运行，便于调试 |

如需把执行工作目录放到其他磁盘，可用 `multica config set workspaces_root <path>` 为当前 profile 持久化根目录，也可在 `daemon start` 或 `daemon restart` 中传入 `--workspaces-root <path>`。flag 的优先级高于 `MULTICA_WORKSPACES_ROOT`，环境变量又高于 profile 配置。修改根目录不会迁移已有的执行目录。

启动时，守护进程会检测 `PATH` 中受支持的 AI 编程工具，并为你有权连接的工作区注册运行时。如果一款工具刚刚安装或登录，重启守护进程即可重新检测。

守护进程至少需要检测到一款内置支持的 AI 编程工具才能启动。安装方法和可执行文件名见[安装 AI 编程工具](/install-agent-runtime)。

## 派发与在线状态

运行时注册后会持续保持连接。新运行入队时，服务器会通知对应守护进程；守护进程也会定期轮询，作为连接中断后的补充。因此运行时在线且有空闲容量时，运行通常会立即开始。

守护进程每 15 秒发送一次心跳。服务端综合心跳与连接状态判断运行时是否在线；守护进程意外退出后，最迟通常会在约 3 分钟内显示为离线。

![一台在线电脑的运行时详情：同一守护进程注册了 7 个运行时，每款检测到的 AI 编程工具各占一行，均显示在线状态与 CLI 版本](/images/docs/runtime-machine-detail.webp)

运行时离线时：

- 已经排队的运行会等待运行时恢复，只有当它心跳缺席超过重连宽限期**且**该运行自己也已排队满这么久时才会失败；所以运行时只是忙的话积压会一直保留，指派给已离线运行时的工作也仍然有完整一个宽限期可以等待。
- 正在执行的运行会失败；符合条件的任务或对话运行可以自动重试。
- 守护进程重新启动后，会重新注册运行时，并回收上一次没有正常结束的运行。
- 离线超过 7 天且没有任何智能体（包括已归档的）绑定的运行时，会被自动清理。

详细状态和重试规则见[运行](/tasks)。

## 并发限制

一台守护进程默认最多同时执行 20 次运行；每个智能体默认最多同时执行 6 次。实际并发取两者中的较小值。

达到上限后，新运行会继续排队。你可以在智能体设置中调整单个智能体的并发数，也可以通过 `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` 调整整台电脑的上限。并行执行会同时占用机器性能、工具账号额度和同一工作目录。

## 私有与公开

本地运行时默认是**私有**的：只有运行时所有者可以在它上面创建智能体。工作区的 owner、admin 也不例外——运行时是别人的电脑，在上面跑智能体消耗的是对方的机器和工具凭据。

只有运行时所有者可以把它改为**公开**——管理员可以重命名或删除运行时，但要不要共享由所有者决定。公开后，工作区中的其他成员也可以选择这条运行时；这不会分享底层 AI 编程工具的登录凭据，只是允许成员把智能体的执行路由到这台电脑。

## 运行时虚拟屏幕

在受支持的 Mac 上，每个运行时可以拥有一个受管虚拟屏幕。在该运行时的屏幕控制中启用或停用。屏幕属于运行时，不属于某次运行或某个观看窗口；关闭镜像窗口后，已启用的屏幕仍在后台保留。同一运行时的多次运行排队取得独占 GUI 控制权，普通代码任务可以独立执行。

镜像仅供观看。在运行时虚拟屏幕与实体显示器之间切换，只会改变观看来源，不会授权智能体控制实体显示器。观看另一台电脑也不代表获得本机接管权限。

### 权限与应用支持

原生宿主包含在 macOS arm64 和 Intel 的 Multica 可执行文件中，需要当前系统提供虚拟显示 API、用于捕获画面的屏幕录制权限，以及用于控制应用的辅助功能权限。仅创建显示器不代表已获得画面捕获或应用控制权限。无需安装独立驱动或辅助应用。Linux、Windows、未包含原生支持的构建，以及缺少所需 API 的 Mac 无法提供这项虚拟屏幕能力。只升级客户端不会为旧守护进程增加能力。

请在 macOS **系统设置 → 隐私与安全性**中，为系统显示的已安装 Multica 身份自行授予权限。开发终端或另一个构建已有权限，不代表已安装的 Desktop 也有权限。诊断不会申请或重置权限。权限未知、权限被拒绝、来源不可用或运行时断开时，均不能视为已准备好执行 GUI 操作。

受管工具可以发现已安装应用，并列出运行时已有的受管窗口。后续运行可以复用这些窗口，包括人工介入后归还的窗口，但执行动作前必须重新观察。发现应用或列出窗口本身不会启动、移动或接管窗口。

受管工具使用目标应用支持的辅助功能操作。生产环境的 PID 定向输入需要经过审核的应用、系统与动作变体证据（键盘动作还包括输入源），还需要由代码配置的完成校验器确认目标已处理输入并产生实际效果。当前生产策略尚未启用 PID 动作；成功投递不等于目标已经完成处理。应用无法保持在受管屏幕内，或无法安全接受后台输入时，需要人工介入。这些保证覆盖受管工具，不覆盖智能体可能调用的全部命令或外部 MCP，也不构成操作系统沙箱。

只读镜像和智能体观察使用不同的数据路径。智能体观察可能包含交给 AI 提供方的截图和辅助功能内容。请确认这些内容可以用于该任务，再放入受管应用。

### 人工接管与清理

运行需要帮助时，会先冻结 GUI 动作，再停止原运行。同一台电脑上的所有者可以明确接管、完成必要步骤并归还控制。归还经过验证后，继续操作会创建关联的后续运行，不会把原运行原地恢复。后续运行必须先观察当前窗口，再执行新动作。无法续接时，需要用户明确选择发起新运行。

如果启动失败时还没有受管窗口，本机所有者可以查看可安全选择的窗口，并明确确认认领。认领只登记该窗口，不会自动移动或激活它；候选标题仅保留在本机 Desktop。归还到虚拟屏幕后，必须有新的观察与已验证的归还回执，才能继续。状态报告尚未确认时，接管流程保持等待。远程观看者可以请求帮助，但不能选择本机候选窗口或完成本机接管。

不再需要虚拟屏幕时，请停用它。停用会等待输入和画面捕获停止，再释放显示器；关闭观看窗口只结束观看。清理、归还或显示器身份无法确认时，应保持阻塞状态并查看错误，不能把超时当作清理成功，也不能重放结果不确定的动作。重启或修改权限后，请重新检查当前运行时状态。

### 检查安装包

在源码目录中检查准备使用的具体应用：

```bash
pnpm --filter @multica/desktop exec node scripts/vscreen-native-smoke.mjs \
  --app /absolute/path/Multica.app --scenario package \
  --evidence /absolute/path/new-evidence-directory
```

`package` 报告记录应用身份、内置可执行文件路径与 SHA-256、架构、链接的框架、版本与 commit，以及签名校验结果。临时签名会明确标为 ad-hoc，不代表通过公证。`diagnostics` 执行不会弹出权限请求的原生能力与权限预检。默认直接启动内置可执行文件，只记录该次调用的权限，不证明 Desktop 的 TCC 归属。缺少权限或旧版本没有诊断命令时，会返回非零结果。

添加 `--launcher desktop`，可通过所选 App 的隔离主进程及已验证的内置可执行文件运行诊断或受支持的 GUI 场景。这会启动真实 App 实例，但不加载正常账户与会话启动流程。`desktop_launch_verified` 只确认进程链，不代表 `tcc_attribution_verified`。两种启动方式都不会申请、授予或重置权限。

GUI 场景必须显式传入 `--allow-gui` 或设置 `MULTICA_RUN_VSCREEN_GUI_SMOKE=1`。它们使用一次性测试资源，默认不录制主实体屏幕。每份报告分别保留验证范围与清理结果：

| 场景 | 验证内容 | 通过不代表 |
| --- | --- | --- |
| `lifecycle`、`sources` | 创建测试专用显示器，核对显示器与来源身份，再验证释放。 | 应用输入或渲染器播放已通过。 |
| `video` | 从虚拟显示器捕获三个 H264 样本，记录参数集、时间戳与哈希。 | 渲染器播放或端到端延迟已通过。 |
| `background-input` | 在复制内置文件创建的测试应用中验证 AX 点击、值修改、新观察，以及拒绝未经认证的 PID 输入。 | 已验证实际安装应用、正向 PID 动作、输入法或前台连续输入。 |
| `takeover` | 通过测试专用执行提供方与本机回环测试后端，执行停止与撤销、本机所有者转移、虚拟屏归还、新观察、回执与后续运行观察。 | 真实数据库、Desktop 界面、真实模型或人工接管已验收；测试应用的人工阶段由脚本驱动。 |
| `input-qualification` | 在同包一次性测试应用中实验验证 PID 点击、Unicode、按键、滚动与拖拽效果，并核验目标完成 ACK 和新观察。必须使用 `--launcher desktop`。 | 已认证生产应用。只有显式选择 `--interactive` 且用户完成独立输入窗口中的挑战，才能取得该人工阶段的证据；否则前台输入保持未验证。 |
| `performance` | 动态虚拟画面、两个 Chromium 观看端、渲染与延迟观测、资源采样和清理循环。 | 已测得实体屏幕实际显示延迟、测试专属 GPU 消耗，或用本机回环证明局域网验收。 |

`sources` 和 `background-input` 是规范名称；`source` 和 `input` 仍可作为别名。交互式资格实验不会替用户写入挑战文本，也不会自动激活输入窗口。它的人工测试结果不认证任意已安装应用，也不能替代生产证据。

正式性能验收至少需要运行 30 分钟并完成 30 次生命周期循环。短时或调试运行不算验收。默认会话使用同机回环连接：`localMeasurement` 可以通过，但缺少局域网证据时，总体评估仍会阻塞。

`all` 执行从 `lifecycle` 到 `performance` 的六个必需场景，不包含实验性 `input-qualification`。它的 `missingCoverage` 门禁独立于各测试应用结果：生产 PID 正向动作、实际应用兼容性、前台连续输入、Desktop 界面、数据库、人工接管与局域网覆盖都需要单独证据。清理无法确认时，不会继续启动后续 GUI 场景。打包、诊断或某个测试场景通过，不代表这些剩余门禁也已通过。


#### 受控远程性能观看端

远程观看仅用于 `performance` 和 `all`，必须同时提供 `--remote-viewer-config` 和 `--allow-remote-viewer`，并保留宿主的 GUI 显式许可。`all` 中只有性能子场景会读取此配置或启动远程进程；其他覆盖门禁仍独立判断。执行前，需要分别获得第二台机器和宿主原生 GUI 操作的授权。

配置必须是绝对路径指向的 JSON 普通文件，由当前用户拥有，权限为 `0600`，不是符号链接、只有一个硬链接，且不超过 64 KiB。仅接受以下全部必需字段：

| 字段 | 要求 |
| --- | --- |
| `schema_version` | `1`。 |
| `host` | 明确的 DNS 名称或 IPv4 地址，不接受 SSH 别名、通配符或 IPv6 地址。 |
| `port` | 1 到 65535 的整数。 |
| `user` | 明确的 SSH 账户；首字符为 ASCII 字母、数字或下划线，其余字符可含字母、数字、下划线、点和连字符，最长 64 个字符。 |
| `known_hosts_file` | 独立文件的绝对路径，只包含一条三字段的主机公钥记录，不含注释、别名或哈希主机名。端口 22 使用与 `host` 完全相同的名称，其他端口使用 `[host]:port`。支持 `ssh-ed25519`、`ecdsa-sha2-nistp256` 和 `ssh-rsa`。 |
| `host_key_sha256` | 与该主机公钥匹配的 `SHA256:` 指纹，不含 base64 填充。 |
| `identity_file` | 用于非交互认证的已有私钥文件绝对路径。 |
| `remote_node` | 远端已有 Node 可执行文件的 Unix 绝对路径。 |
| `remote_repo` | 远端匹配版本仓库的 Unix 绝对路径。 |
| `worker_hash` | 下方 worker 命令生成的匹配 SHA-256，长度为 64 个小写十六进制字符。 |

两个被引用的本地文件也必须由当前用户拥有，权限为 `0600`，是非符号链接、单硬链接的普通文件，且不超过 64 KiB。远端 Node 与仓库路径仅允许 ASCII 字母、数字、`_`、`.`、`/` 和 `-`；拒绝 `..` 路径段、空格、`~` 和 shell 语法。SSH 只使用指定私钥与固定主机公钥记录的私有快照，不使用 SSH agent、密码提示、已有 SSH 配置、全局 known_hosts 备用记录或转发。

远端 Mac 或 Linux 机器必须已有匹配的 worker 源码、仓库根目录声明的 `@playwright/test` 依赖及 Chromium。工具不会发现或安装这些前置条件。在两端仓库根目录分别运行并比较 worker 哈希；此命令不会启动 SSH 或浏览器：

```bash
node apps/desktop/scripts/vscreen-remote-worker.mjs --hash
```

准备好私有配置，以及包含匹配画面发送端与观看端实现的新安装包后：

```bash
pnpm --filter @multica/desktop exec node scripts/vscreen-native-smoke.mjs \
  --app /absolute/path/Multica.app --scenario performance --launcher desktop \
  --allow-gui --remote-viewer-config /absolute/path/private-remote-viewer.json \
  --allow-remote-viewer --evidence /absolute/path/new-remote-evidence
```

画面发送端的授权 nonce 留在宿主，不要加入配置或命令行；信令请求由宿主转发给发送端。worker 启动全新的无头 Chromium 上下文，不接入用户浏览器配置。

远程源码支持不等于局域网验收通过。通过还需要观测到不同机器身份、匹配的来源与证书及会话证据、实际选中的直连 UDP 连接对，以及两端已确认的实体网卡直连网段路由，并满足原有时长、资源和清理门禁。缺少系统工具、路由未知、回环、隧道或中继都会阻塞。机器身份属于对系统的信任证据，不是硬件证明。本机无头测试不能证明局域网覆盖；仍需要真实两机与原生操作授权，以及通过实际观测。

## 自定义运行时配置

如果团队使用内部 wrapper、固定版本的可执行文件，或需要为一款兼容工具追加固定参数，可以创建**自定义运行时配置**。

自定义配置不会增加新的通信协议。创建时仍需选择一种 Multica 已支持的协议族（工具的对接协议类型，见 [AI 编程工具对照](/providers)）；命令本身必须与该协议兼容。

### Task 运行时环境

守护进程启动智能体 task 时，会把 task 上下文注入运行时进程。这些值由守护进程管理；智能体的自定义环境无法覆盖任何 `MULTICA_` 变量或 task 临时目录变量。

下表列出自定义运行时目前可以使用的变量。它不是完整清单，也不是有版本保证的 API。集成只能依赖标为**集成契约**的 5 个变量；其余变量仅供参考，后续可能变化。

| 变量 | task 中的值 | 稳定性 |
| --- | --- | --- |
| `MULTICA_TOKEN` | task 级 `mat_` API 凭据 | **集成契约** |
| `MULTICA_TASK_ID` | 当前 task 的 ID | **集成契约** |
| `MULTICA_AGENT_ID` | 被指派智能体的 ID | **集成契约** |
| `MULTICA_WORKSPACE_ID` | task 所属工作区的 ID | **集成契约** |
| `MULTICA_SERVER_URL` | 守护进程选定的 Multica 服务地址 | **集成契约** |
| `MULTICA_TASK_CONFIG_ROOT` | 私有的 task 本地 Multica CLI 配置根目录 | 仅供参考 |
| `MULTICA_TASK_WORKSPACES_ROOT` | 守护进程管理的 task 工作区根目录 | 仅供参考 |
| `MULTICA_AGENT_NAME` | 被指派智能体的显示名称 | 仅供参考 |
| `MULTICA_DAEMON_PORT` | 本地守护进程的健康检查/API 端口，供 `multica repo checkout` 等仅限 task 的命令使用 | 仅供参考 |
| `MULTICA_TASK_SLOT` | 守护进程全局并发池中的槽位，可用于 GPU 等按槽位编号的资源 | 仅供参考 |
| `TMPDIR` | 当前 task 的私有临时目录；也会以 `TMP` 和 `TEMP` 提供给跨平台工具 | 仅供参考 |

使用 `MULTICA_TOKEN` 发起请求时，作者身份由服务端决定；任务评论等写入操作会归属到被指派的智能体和当前 task。令牌的完整绑定关系、权限、归属方式、最长 24 小时的有效期和清理规则见[智能体执行的临时令牌](/auth-tokens#智能体执行的临时令牌)。

<Callout type="warning">
这些值存在于运行时进程的实际环境中。运行时启动的任何子进程默认都会继承全部变量，包括 `MULTICA_TOKEN`。如果子进程不应持有该凭据，必须显式移除；不要假定进程之间存在并没有的隔离。反过来，有些工具会过滤自己的子进程环境，因此可能需要显式放行变量。例如，Codex 的 shell 工具会丢弃名称中含有 `TOKEN`、`KEY` 或 `SECRET` 的变量，所以守护进程会安装托管的 shell 策略，放行所需的 task 变量。令牌只能存在于进程环境中，不得写入 prompt、日志、仓库文件或持久配置。子进程与父 task 共享身份和权限，不会获得新的独立作用域身份。
</Callout>

### 创建配置

只有工作区 owner 和 admin 可以创建、修改或删除自定义运行时配置：

1. 打开 **运行时**，进入已经安装该命令的电脑。
2. 点击**添加自定义运行时**。
3. 选择命令实际兼容的协议族。
4. 填写名称、命令和固定参数，然后保存。

配置会在工作区内共享。每台已连接电脑会自行查找这个命令；只有能在 `PATH` 中解析到它的电脑才会注册对应运行时。创建配置不会自动安装命令，也不会替其他成员完成工具登录。

这里填写的是可执行文件和参数，不是 shell 脚本。可以使用普通参数、引号和反斜杠转义，但不能使用管道、重定向、`&&`、`;`、反引号或环境变量展开。需要这些行为时，把它们放进 wrapper script，再把该脚本作为命令填写。

### 参数的排列顺序

命令字段里填写的内容会紧跟在可执行文件之后，排在 Multica 追加的参数之前：

```text
<你的命令> <你的固定参数> <Multica 的协议参数> <Agent 的自定义参数>
```

带子命令的 wrapper 正是依靠这个顺序才能工作。如果命令是 `ccms start q36`，工具会先看到 `start q36`，在 Multica 的 `-p` 等参数到达之前完成子命令选择——这类 wrapper 只接受这一种顺序。

此前这里填写的参数是追加在最后的。多数 flag 形式的命令在两种位置下解析结果相同，但并非全部——如果某个命令区分全局 flag 和子命令 flag，它就会在意 flag 的位置。如果你已经配置了带固定参数的 profile，升级后请发起一次运行，确认它仍能正常启动。

另有两点需要注意：

- **冲突时以 Multica 的值为准。** 如果固定参数设置了 Multica 也会设置的 flag，Multica 的值排在后面并最终生效。最典型的是：在 Agent 上选择的模型会覆盖 profile 里固定的 `--model`。若要为所有人固定模型，请把 Agent 的模型字段留空。
- **协议关键 flag 会被忽略。** `-p`、`--output-format`、`--input-format`、`--permission-mode` 以及其他协议族的对应 flag 会从固定参数中被剔除，因为覆盖它们会切断 daemon 与工具之间的通信。子命令和其他位置参数始终原样传递。

如果 Desktop 启动的守护进程找不到终端里能够执行的命令，可以为当前电脑设置绝对路径：

```bash
multica runtime profile set-path <profile-id> --path /absolute/path/to/command
```

移除路径覆盖：

```bash
multica runtime profile unset-path <profile-id>
```

修改配置只影响之后领取的运行。删除配置前，需要先处理仍绑定在对应运行时上的活动智能体。只删除某台电脑上的运行时实例并不会删除配置，运行中的守护进程还会重新注册它。

## 运行时离线的排查

按以下顺序检查：

1. 运行 `multica daemon status`，确认守护进程已经启动。
2. 运行 `multica daemon logs -f`，查看登录、网络或工具检测错误。
3. 在同一运行环境中执行 `command -v <工具命令>`，确认守护进程能够找到它。
4. 打开 Multica 的**运行时**页面，检查目标电脑和对应的 AI 编程工具是否显示在线。
5. 工具刚安装、路径刚修改或配置刚更新时，运行 `multica daemon restart`。

仍未解决时，参见[故障排查](/troubleshooting)。
