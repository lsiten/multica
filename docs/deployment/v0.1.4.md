# v0.1.4：MR 发布检查修复与已有部署升级

本版替代 v0.1.3，修复 Handler 快照复制 MR 代理互斥锁的问题、MR 文案的国际化检查，以及三个通知机器人并发索引创建失败后的重试清理。已发布迁移 SQL 保持不变。服务端仍只做鉴权与临时转发，不新增 MR 数据表。

## 发布门槛

等待本提交的 **CI** 与 v0.1.4 的 **Fork Images / publish** 全部通过，再升级。仅镜像构建成功不代表测试通过。本次仍不发布桌面安装包。

- `ghcr.io/lsiten/multica-backend:v0.1.4`
- `ghcr.io/lsiten/multica-web:v0.1.4`

## 已有 Docker Compose 部署

完整的备份、配置保留、运行时更新和回滚步骤见 [已有部署升级指南](./v0.1.3.md)。执行该指南时，将所有 `v0.1.3` 替换为 `v0.1.4`，提取容器名中的 `v013` 替换为 `v014`。不要混用两个版本。

关键顺序：

1. 保留当前 `.env`、JWT 密钥、集成加密密钥、自定义 Compose 参数和卷名；不要覆盖为示例配置。
2. 先拉取新版镜像，等待运行中的任务结束，在维护窗口备份数据库、上传卷及运行时的工作区。保留旧镜像的回滚标签。
3. 将已有 `.env` 中的 `MULTICA_IMAGE_TAG` 改成 `v0.1.4`，重新创建 backend/frontend，保留 PostgreSQL 与数据卷。
4. 检查迁移和启动日志，确认 `/api/config` 返回 `server_version: "v0.1.4"`、`local_review_supported: true`。
5. 更新任务所属机器的 daemon；桌面开发版需要重新运行 `pnpm dev:desktop`，仅升级服务器不会更新本机二进制。

完成备份后，在原部署目录执行（若原来使用 `-p`、`--env-file` 或附加 `-f`，保留同样参数）：

```bash
MULTICA_IMAGE_TAG=v0.1.4 docker compose -f docker-compose.selfhost.yml pull backend frontend
MULTICA_IMAGE_TAG=v0.1.4 docker compose -f docker-compose.selfhost.yml up -d --no-build --no-deps backend frontend
docker compose -f docker-compose.selfhost.yml ps
docker compose -f docker-compose.selfhost.yml logs --tail=100 backend
curl -fsS https://multica.lene.fun/api/config
```

不要运行 `docker compose down -v`。应用镜像回滚不会自动撤销数据库迁移；具体回滚见上述指南。

## MR 仍提示不支持时

- 先确认客户端实际连接地址对应的 `/api/config`，而不是只看仓库 tag 或镜像标签。
- 若服务端已返回支持，关闭并重开 MR 弹窗；桌面端仍需确认已加载新版主进程、preload 和 daemon。
- 对应运行时的桌面端优先直连本机 daemon；其他机器和普通网页通过后端代理。首次识别旧目录可能需要服务端核对任务身份。
- 不要仅根据目录路径相同就跳过运行时身份校验；不同机器可能有同名路径。

企业微信发布通知表示镜像发布已验证，不表示已代为升级生产服务器。
